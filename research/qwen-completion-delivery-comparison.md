# Qwen background completion delivery compared with Agora Voice-to-ACP Local

Research date: 2026-08-20  
Qwen source inspected: [`QwenAudio/qwen-audio-agent` commit `774aaf4f820e3ac19938587b8511ac74a30b5d73`](https://github.com/QwenAudio/qwen-audio-agent/tree/774aaf4f820e3ac19938587b8511ac74a30b5d73) (`main` at the time of inspection)  
Local source inspected: `recipe-agent-acp-local` commit `60b86099ea04422ff50ec6d8bd4d2d29cac6e12c`

## Conclusion

Qwen does not wait for the voice model to ask for status. A terminal backend
result creates a durable pending notification, and the active voice Gateway
claims it, injects bounded result material into Realtime, requests an audio-only
response, and confirms the notification from a client playback receipt. If no
voice frontend is ready, the notification remains recoverable.

The local recipe already has the right durable starting point:
`pending_delivery`, `sending`, `accepted`, and `delivery_unknown`. What is
missing is the delivery coordinator between TaskRuntime completion and the
active Agora Agent session. The smallest v0.1 should copy Qwen's durable
pending/claim/retry boundary, but use the existing deterministic
`session.say(..., priority="APPEND")` path. It should not copy Qwen's second LLM
turn, browser playback protocol, batching, or cross-session claim machinery yet.

## Qwen's actual flow

### 1. Completion originates in the backend task ledger

After the runner resolves, `TaskManager` stores `completed` plus the final
result (or `failed` plus the error). Its `finally` block sets
`notificationStatus = "pending"`, then emits both the terminal task event and
`task.notification.pending` ([source](https://github.com/QwenAudio/qwen-audio-agent/blob/774aaf4f820e3ac19938587b8511ac74a30b5d73/server/src/task/task-manager.mjs#L642-L703)).
The notification state is part of the public/persisted task receipt; a saved
`delivering` claim is reset to `pending` on restart
([source](https://github.com/QwenAudio/qwen-audio-agent/blob/774aaf4f820e3ac19938587b8511ac74a30b5d73/server/src/task/task-manager.mjs#L180-L213)).

### 2. Transport is in-process publish/subscribe plus a durable ledger

`TaskManager.emit()` snapshots the task and calls every registered listener;
one observer cannot break the queue
([source](https://github.com/QwenAudio/qwen-audio-agent/blob/774aaf4f820e3ac19938587b8511ac74a30b5d73/server/src/task/task-manager.mjs#L291-L330)).
The voice Gateway subscribes to these events. For a pending notification in its
session it claims the task rather than directly speaking the event
([source](https://github.com/QwenAudio/qwen-audio-agent/blob/774aaf4f820e3ac19938587b8511ac74a30b5d73/server/src/voice/realtime-gateway.mjs#L811-L878)).

This is not a backend-to-browser push guarantee by itself. The persisted
notification ledger is the source of truth; the event is only a prompt to try
delivery.

### 3. Active-session claiming and injection

Claims transition `pending -> delivering`, bind a claimant ID and timestamp,
and are filtered by owner and normally by originating session. A claimant-checked
operation marks the notification delivered
([source](https://github.com/QwenAudio/qwen-audio-agent/blob/774aaf4f820e3ac19938587b8511ac74a30b5d73/server/src/task/task-manager.mjs#L831-L881)).
Claims are renewed while delivery is active, released back to `pending` on an
abandoned connection, and reclaimed after a TTL
([source](https://github.com/QwenAudio/qwen-audio-agent/blob/774aaf4f820e3ac19938587b8511ac74a30b5d73/server/src/task/task-manager.mjs#L884-L938)).

The Gateway records the result in conversation history, queues it in
`AnnouncementManager`, and retains task/turn IDs as response correlation
metadata
([source](https://github.com/QwenAudio/qwen-audio-agent/blob/774aaf4f820e3ac19938587b8511ac74a30b5d73/server/src/voice/realtime-gateway.mjs#L564-L590)).
The manager waits while the user is speaking, a user turn is pending, audio is
queued, or another response is playing
([source](https://github.com/QwenAudio/qwen-audio-agent/blob/774aaf4f820e3ac19938587b8511ac74a30b5d73/server/src/voice/announcement/announcement-window.mjs#L1-L84)).

For delivery it creates bounded structured result material, injects it once as
a Realtime conversation item, and requests a new response. Retries reuse the
same active batch and do not inject the context twice
([source](https://github.com/QwenAudio/qwen-audio-agent/blob/774aaf4f820e3ac19938587b8511ac74a30b5d73/server/src/voice/announcement/announcement-manager.mjs#L235-L343)).

### 4. Speech is generated by the Realtime model

`RealtimeFrontend.injectResult()` sends a `conversation.item.create`, followed
by `response.create`
([source](https://github.com/QwenAudio/qwen-audio-agent/blob/774aaf4f820e3ac19938587b8511ac74a30b5d73/server/src/voice/realtime-provider.mjs#L393-L414)).
For DashScope, the response requests the provider's supported output modalities,
sets `tool_choice: "none"`, and supplies result-specific instructions
([source](https://github.com/QwenAudio/qwen-audio-agent/blob/774aaf4f820e3ac19938587b8511ac74a30b5d73/server/src/voice/providers/dashscope.mjs#L94-L111)).
The resulting audio deltas travel over Qwen's Gateway WebSocket to its client
([source](https://github.com/QwenAudio/qwen-audio-agent/blob/774aaf4f820e3ac19938587b8511ac74a30b5d73/server/src/voice/realtime-gateway.mjs#L1127-L1154)).

Thus Qwen's completion announcement is a second LLM-generated voice turn, not a
direct TTS call with the backend's final text.

### 5. No voice session and reconnect behavior

If the Realtime frontend is not ready, `AnnouncementManager` retains the active
batch, renews its lease, and retries with exponential delays; retries are
bounded, after which the claim is released
([source](https://github.com/QwenAudio/qwen-audio-agent/blob/774aaf4f820e3ac19938587b8511ac74a30b5d73/server/src/voice/announcement/announcement-manager.mjs#L202-L231),
[source](https://github.com/QwenAudio/qwen-audio-agent/blob/774aaf4f820e3ac19938587b8511ac74a30b5d73/server/src/voice/announcement/announcement-manager.mjs#L273-L365)).

If only the provider connection drops while the client remains connected, the
Gateway reconnects and then flushes announcements. When the provider becomes
ready it also re-announces pending permissions and claims pending notifications
([source](https://github.com/QwenAudio/qwen-audio-agent/blob/774aaf4f820e3ac19938587b8511ac74a30b5d73/server/src/voice/realtime-gateway.mjs#L1492-L1548)).

If the entire voice client disconnects, the manager closes and releases its
claims. A later connection calls `claimPendingNotifications()` without task IDs;
that mode may include older sessions belonging to the same owner
([source](https://github.com/QwenAudio/qwen-audio-agent/blob/774aaf4f820e3ac19938587b8511ac74a30b5d73/server/src/voice/realtime-gateway.mjs#L811-L826),
[source](https://github.com/QwenAudio/qwen-audio-agent/blob/774aaf4f820e3ac19938587b8511ac74a30b5d73/server/src/voice/realtime-gateway.mjs#L2125-L2146)).

### 6. Deduplication and stale-response protection

Qwen uses several separate guards:

- persisted `pending/delivering/delivered` state and a claimant ID prevent two
  live frontends from owning the same result;
- a renewable claim TTL recovers crashed deliveries;
- `contextInjected` prevents duplicate Realtime conversation items during a
  retry;
- `deliveryGeneration` and active-batch identity prevent a late asynchronous
  result from mutating a paused or replaced batch;
- only task IDs actually represented in the bounded batch can be acknowledged
  ([source](https://github.com/QwenAudio/qwen-audio-agent/blob/774aaf4f820e3ac19938587b8511ac74a30b5d73/server/src/voice/announcement/announcement-manager.mjs#L235-L266),
  [source](https://github.com/QwenAudio/qwen-audio-agent/blob/774aaf4f820e3ac19938587b8511ac74a30b5d73/server/src/voice/announcement/announcement-manager.mjs#L273-L365));
- playback receipts are accepted only from the active output-owning client for
  a known response ID
  ([source](https://github.com/QwenAudio/qwen-audio-agent/blob/774aaf4f820e3ac19938587b8511ac74a30b5d73/server/src/voice/realtime-gateway.mjs#L2062-L2093)).

One important source discrepancy exists. `docs/architecture.md` says delivery
is marked after playback finishes
([source](https://github.com/QwenAudio/qwen-audio-agent/blob/774aaf4f820e3ac19938587b8511ac74a30b5d73/docs/architecture.md#L221-L231)),
but current code calls `confirmMany()` when playback **starts**
([source](https://github.com/QwenAudio/qwen-audio-agent/blob/774aaf4f820e3ac19938587b8511ac74a30b5d73/server/src/voice/realtime-gateway.mjs#L662-L680)).
It also treats an explicit user interruption as dismissal/delivery rather than
replaying the announcement
([source](https://github.com/QwenAudio/qwen-audio-agent/blob/774aaf4f820e3ac19938587b8511ac74a30b5d73/server/src/voice/realtime-gateway.mjs#L683-L703)).
Therefore Qwen does not prove that the user heard the complete result.

### 7. Permission delivery is the closest parallel

Qwen derives the current permission request from active authoritative task
state, keeps an in-memory announced-ID set, waits for a quiet output window,
injects the request into Realtime, and rechecks that it is still pending just
before speaking
([source](https://github.com/QwenAudio/qwen-audio-agent/blob/774aaf4f820e3ac19938587b8511ac74a30b5d73/server/src/voice/realtime-gateway.mjs#L227-L284)).
When another channel resolves it, Qwen cancels the matching queued response and
silently updates model context so it will not ask again
([source](https://github.com/QwenAudio/qwen-audio-agent/blob/774aaf4f820e3ac19938587b8511ac74a30b5d73/server/src/voice/realtime-gateway.mjs#L879-L915)).

The local recipe already has the analogous active-session primitive:
`ManagedContextSynchronizer` updates authoritative permission context and calls
`session.say(..., priority="APPEND", interruptable=True)` for speech
(`server/src/architecture_validation/managed.py`, lines 38-68 at the inspected
local commit). Completion delivery should share this session ownership and
serialization boundary, not create an unrelated voice channel.

### 8. Status query remains the fallback

Qwen's `get_agent_task_status` returns terminal result/error directly. If that
result still has a pending/delivering notification, the response is tagged as
consuming that notification so its playback also confirms delivery
([source](https://github.com/QwenAudio/qwen-audio-agent/blob/774aaf4f820e3ac19938587b8511ac74a30b5d73/server/src/voice/tools/tool-call-handler.mjs#L827-L979)).
A delegated status query becomes a hidden control task and its answer returns
through the same asynchronous announcement path
([source](https://github.com/QwenAudio/qwen-audio-agent/blob/774aaf4f820e3ac19938587b8511ac74a30b5d73/docs/architecture.md#L107-L114)).

## Local gap

The local TaskRuntime already saves a bounded/redacted `FinalPresentation` and
sets `delivery_state = "pending_delivery"` before transitioning Work to
`completed` (`server/src/task_runtime/runtime.py`, lines 257-278, and
`server/src/task_runtime/store.py`, lines 373-399). Its public status tool
returns the final presentation and delivery state, so manual status lookup is a
working fallback (`server/src/managed_ingress/tools.py`, lines 74-87 and
128-151).

However, there is currently:

- no completion subscriber or dispatcher;
- no store operation that claims `pending_delivery` or commits another delivery
  state;
- no durable association between a Work and the exact originating Agora Agent;
- no retry or recovery trigger when a Managed Agent session becomes available;
- no playback receipt from Agora Managed Agent comparable to Qwen's browser
  receipt.

`Agent` does retain active Managed Agent sessions by exact `agent_id`, and each
MCP capability binding contains `workspace_id`, `workspace_generation`, and
`agora_agent_id` (`server/src/agent.py`, lines 304-388, and
`server/src/managed_ingress/models.py`, lines 17-25). Those are sufficient to
perform a safe active-session check.

## Smallest v0.1 pattern to copy

1. Add one in-process completion notification from TaskRuntime immediately
   after the final receipt is committed. The database remains authoritative;
   the event only wakes a delivery coordinator.
2. Persist the delivery target captured at `start_work`: exact
   `agora_agent_id`, Workspace ID, and Workspace generation. Do not infer the
   target from "latest active session" at completion time.
3. Add compare-and-set store operations for
   `pending_delivery -> sending -> accepted|delivery_unknown`. A known
   pre-submission failure may return to `pending_delivery`; an ambiguous network
   outcome must become `delivery_unknown` rather than automatically replaying.
4. Immediately before delivery, verify that the exact originating Agent session
   is still locally active and its Workspace generation still matches. If not,
   leave the result `pending_delivery`; do not speak it into a different active
   conversation.
5. Serialize completion speech with the same per-session boundary used for
   permissions and call the existing deterministic
   `session.say(final_presentation.speech, priority="APPEND",
   interruptable=True)`. A successful API return means `accepted`, not "heard in
   full".
6. Keep `get_work_status` as the durable fallback. In v0.1, a reconnect may
   retrieve the result on request; automatic cross-session recovery should wait
   until the product defines an explicit stable owner and replay policy.

This solves the observed active-conversation case without introducing another
LLM turn or a second ingress path. It also fits the existing local delivery
state vocabulary.

## Patterns not to copy yet

- **Do not inject the backend result into Managed LLM context for another model
  rewrite.** Qwen can do this because it owns the Realtime socket, response
  correlation, and audio stream. The local recipe already has bounded speech
  material and a Managed Agent `say` path.
- **Do not claim playback-complete semantics.** Qwen's current implementation
  marks delivered at playback start, while the local Managed Agent path has no
  equivalent client receipt.
- **Do not copy batching.** One Work completion per `say` call is simpler and
  preserves the current result/work correlation.
- **Do not copy cross-session owner recovery in v0.1.** Qwen has a stable owner
  identity and renewable claimant leases. The local recipe currently has an
  exact Agora Agent and Workspace generation, which is safer but session-bound.
- **Do not copy Qwen's full announcement window.** Start with the SDK's `APPEND`
  serialization plus exact-session revalidation. Add richer quiet-window and
  playback behavior only if live tests show a concrete conflict.
- **Do not use retry-on-unknown.** Without a playback or acceptance idempotency
  key, retrying an ambiguous `say` outcome can duplicate speech.

## Acceptance checks for the later implementation

- Active exact session: a completed Work invokes one `APPEND` `say`, then stores
  `accepted`.
- No active exact session: no other Agent is called; state stays
  `pending_delivery`; status still returns the full result.
- Workspace changed or old Agent stopped between claim and send: delivery is
  rejected before `say`.
- Known send rejection: state is retryable according to a bounded policy.
- Ambiguous timeout/disconnect after submission: state becomes
  `delivery_unknown` and is not automatically replayed.
- Duplicate completion event: compare-and-set prevents a second `say`.
- Permission and completion arriving together: one per-session serializer
  preserves deterministic ordering; permission should take precedence.
